## D. Entity relationships

```
Customer ──(1)────────────────────────────┐
   id UUID                                │ customer_id (nullable, SET NULL)
                                          ▼
Reservation ── reservation_date + time + table ──► Restaurant Table
   id UUID / code (RSV-308)                  ▲  id UUID / label (T-01), capacity, status
   guest_name (snapshot; walk-ins OK)        table_id (nullable, SET NULL)
   status pending|confirmed|completed|cancelled
```

- **Customer → Reservation:** `customer_id` nullable (a reservation may be a walk-in with no `customers`
  row); `ON DELETE SET NULL` — deleting a customer keeps the reservation but clears the link; `guest_name`
  is the durable snapshot.
- **Reservation → Table:** `table_id` nullable `ON DELETE SET NULL`. A reservation can exist without a table.
- **Restaurant Table ← Reservation:** one table can host many reservations over time; conflict is purely a
  **date+time+table** overlap question (no DB constraint enforces it — see E, G).
- **Soft delete:** tables have `deleted_at`; **reservations do NOT** — a "removed" reservation is either a
  `cancelled` status (recommended) or a hard DELETE (RLS-gated). See L.
- **Walk-in reservations** are explicitly supported by the schema (`guest_name` snapshot, nullable
  `customer_id`) — the current form already models this (free-text Customer name). Flag for approval whether
  4D should link existing customer rows (see L).

## E. Reservation lifecycle analysis

The status enum (`pending → confirmed → completed`, with side branch `cancelled`) is the core lifecycle. The
current UI allows arbitrary jumps (any status → any status) via the form select; the DB imposes no order.

- **pending**: default; awaiting staff action.
- **confirmed**: table holds are meaningful here; this is where conflict checking matters most.
- **completed**: guest has arrived/dined; reservation is historical, no longer holds the table.
- **cancelled**: frees the table/time slot; should **not count** against capacity for conflict purposes and
  should be filtered out of "active" reservations (the Tables drawer already does this).

**Recommended lifecycle rules (need approval, L):**
1. Allow the transient transitions pending→confirmed→completed and any→cancelled.
2. **Conflict check** should consider only `pending`/`confirmed` reservations on the same `table_id` +
   `reservation_date` (exclude `completed`/`cancelled`). Can further require a min gap by time if approved.
3. Marking `completed`/`cancelled` frees the table (no conflict).
4. UI: provide status transitions in the drawer/detail (buttons) rather than free-form select, to guide the
   lifecycle — but defer a strict state machine to a later phase unless approved (L).

**Cancellation behavior:** the recommended "delete" is a **status transition to `cancelled`** (non-destructive,
RLS-authorized via `reservations.manage` UPDATE, keeps history). Hard DELETE is RLS-authorized but destructive
and unnecessary for the standard flow; keep it out of the default UI (see C.1/G/L).

## F. Restaurant table lifecycle analysis

The table `status` (`available|occupied|reserved`) is a **live operational flag**, not derived from
reservations today. In the current mock UI the two are decoupled: a table's status and its reservations are
independent.

- `available` — floor-plan default; no active hold.
- `reserved` — currently set manually; semantically should track an active (pending/confirmed) reservation.
- `occupied` — a party is seated; today manual.

**Conflict with 4D scope:** table status writes require `settings.manage` (Owner/Admin only), while
reservation status/table-assignment writes require `reservations.manage` (Owner+Manager). A waiter or manager
could create/confirm a reservation on a table whose `status` is stale (`available` while `reserved`). Two
design options require approval (L):
- **Option 1 (default, no schema change):** keep table `status` as a manually-managed Owner control; the
  reservation flow optimistically checks/sets reservation-level status but does **not** auto-write
  `restaurant_tables.status` (because manager/waiters may lack `settings.manage`). The floor plan shows
  reservation-derived occupancy read-only to non-owners.
- **Option 2 (additive migration later):** introduce a narrow RPC (like the deferred 0007 pattern) that
  updates table status when a reservation is created/confirmed/cancelled, running under a
  permissions/definer rule that respects both `reservations.manage` and `settings.manage`. **Not in 4D
  unless approved** — see G/L.

The floor plan SELECT needs no permission, so read integration is safe for all staff; only the status-write
control is Owner-gated.

## G. Edge cases and concurrency risks (documented; solutions recommended, not implemented)

| # | Edge case | Current behavior | Recommended handling for 4D |
|---|---|---|---|
| 1 | **Double-booking same table** | None — unconditional in-memory insert | **No DB constraint exists.** Add a date+table conflict check in the service/UI: block create/update if another `pending`/`confirmed` reservation overlaps the same `table_id`+`reservation_date` (+time window if approved). Best-effort in app; true serialization needs either a constraint or an atomic RPC (see L). |
| 2 | **Concurrent reservation creation** | N/A (single user) | Two PostgREST inserts can race past the app-level check. Mitigation: optimistic app check + authoritative refetch; if uniqueness is mandatory, the **only** real fix is an **additive migration** (e.g. a partial unique index on `(restaurant_id, table_id, reservation_date)` **excluding** `completed`/`cancelled`, or an atomic booking RPC). **Requires migration approval (J).** |
| 3 | **Table capacity validation** | None | Validate `guests <= table.capacity` on create/confirm (currently not enforced). Reject/surface a clear error tip instead of saving an over-capacity booking. |
| 4 | **Customer deletion with reservations** | N/A | DB already handles it: `customer_id SET NULL`, `guest_name` snapshot preserved → reservation history intact. No 4D action needed beyond using the correct FK semantics. |
| 5 | **Reservation cancellation** | No cancel path | Recommended: status → `cancelled` (UPDATE). Exclude `cancelled`/`completed` from conflict checks and "active" lists. |
| 6 | **Past reservations** | Show all dates forever | Filter/visualize "today" bookings (already done); for conflict checks, ignore past dates. Optional: auto-roll `pending/confirmed` into `completed` past a threshold — **needs approval (L)**. |
| 7 | **Cross-tenant access** | Prevented by RLS already | Every policy re-derives `restaurant_id` from session. Service **never** accepts/client-sends `restaurant_id`. Non-tenant rows are invisible; live-verify (K). |
| 8 | **Rapid double-submit** | Possible | Reuse 4C pattern: `submitting` guard on every mutation; disable while in flight and refetch after. |
| 9 | **UUID vs existing frontend IDs** | UI keys on display codes | Real rows carry uuid `id`; keep display `code`/`label` for humans. Mapper: `Reservation { id?: uuid, code, ... }`, `DiningTable { id?: uuid, label, cap }`. Never mix mock codes with DB uuids (wholesale replace rule from 4B/4C). |
| 10 | **Empty-DB fallback** | Seed shown | Reuse `useCustomers` hydration rule: show seed until real rows exist (clean DB stays on seed for non-destructive UI); do not silently blank the page. Real reads only when real rows present; never mix mock+real. |
| 11 | **UUID/duplicate reservation codes** | length-based `RSV-` | Deferred 0007 codegen RPC is the proper fix; 4D may reuse/keep server `code` (unique per restaurant) and must **not** rely on `s.reservations.length`. If 4D creates reservations with a client-generated code, it risks collision — prefer a server-side additive RPC (**migration decision, after approval**). |
| 12 | **Permission-lite roles** | Controls visible | Gate all write controls by resolved `reservations.manage` / `settings.manage` (C.4). Waiters see read-only reservations + floor plan; managers can't change table status. |

## H. Proposed service/hook architecture (follows 4B/4C exactly)

Data flow: `Supabase (RLS) → typed service (ServiceResult<T>) → hydration/mutation hooks → store (s.*) →
page`. No competing architecture; no direct Supabase in pages; tenant derived server-side / via
`getCurrentIdentity`; never trust client `restaurant_id`.

### H.1 `src/types/database.ts` (already has `ReservationsRow`, `ReservationsInsert/Update`,
`RestaurantTablesRow`, `RestaurantTablesInsert/Update`, `CustomersRow/Insert/Update`) — no duplication.

### H.2 `src/types/index.ts` — extend view models (add optional uuid `id`, keep display fields):

```ts
Reservation {
  id?: string;        // DB uuid when real
  code: string;       // display ref RSV-308 (was `id`)
  cust: string;       // guest_name snapshot
  phone: string;
  date: string;       // YYYY-MM-DD
  time: string;       // 12h display; store ISO/24h via mapper
  guests: number;
  table: string;      // table display label (T-01) for UI
  tableId?: string;   // DB uuid table_id
  customerId?: string;// DB uuid customer_id

DiningTable {
  id?: string;        // DB uuid

```

### H.3 `src/services/reservations.ts` (new) — `ServiceResult<T>`:
- `listReservations(supabase)` — SELECT (`status` mapped to frontend casing), order by date+time.
- `getReservation(supabase, id)` — single with `maybeSingle` (`NOT_FOUND` when missing).
- `createReservation(supabase, input, identity)` — `reservation_code` from approved source (see L/J); derive
  `restaurant_id` from identity; default `status=pending`; `.select().single()`; optimistic conflict/capacity
  pre-check (best-effort) then insert.
- `updateReservation(supabase, id, input)` — subset update (guest fields, date/time/guests/table/status/notes);
  never `restaurant_id`; `maybeSingle`; beat conflict re-check.
- `cancelReservation(supabase, id)` — status → `cancelled` (UPDATE; recommended delete).
- (optional) `deleteReservation(supabase, id)` — hard DELETE (Owner tool; default OFF).
- `reservationRowToView(row)` — single mapper (DB → view incl. casing + relative time).

### H.4 `src/services/tables.ts` (new):
- `listTables(supabase)` — SELECT tenant floor plan (no permission needed), map `capacity`→`cap`,
  uuid `id`, `label`.
- `getTable(supabase, id)`.
- `createTable` / `updateTable` / `softDeleteTable` (set `deleted_at`) — all `settings.manage`-gated
  (default Owner-only UI); `createTable` derives `restaurant_id` from identity and validates `label`
  uniqueness (`restaurant_id,label`).
- `tableRowToView(row)`.

### H.5 `src/hooks/useReservations.ts` (read hydration) + `src/hooks/useReservationActions.ts` (mutations):
mirror `useCustomers`/`useCustomerActions`. `useReservationActions` returns
`{ create, update, cancel, delete }` with `submitting`/`error`, updates `s.reservations`, `notify()`, `toast()`.

### H.6 `src/hooks/useTables.ts` (read) + `useTableActions.ts` (status/CRUD): mirror above; status change is the
smallest, most useful 4D write slice.

### H.7 Pages:
- `Reservations.tsx` — keep calendar + list; replace in-memory save with the service/hook; add Edit drawer or
  modal-driven by uuid; add Cancel; gate write controls by `reservations.manage`.
- `Tables.tsx` — hydrate from `useTables`; status control gated by `settings.manage`; read-only floor plan for

### H.8 Optimistic vs authoritative
- **Optimistic updates only where safe**: table status toggle and reservation status transitions (visible,
  idempotent, low-stakes) may optimistically apply then refetch on error.
- **Authoritative refetch** after create/update/cancel (transactional outcome must be confirmed from the DB);
  refetch the affected slice (as 4C's store update + optional refetch pattern).

## J. Migration requirements (if any — IDENTIFIED, NOT APPLIED)

The audit finds the following **potential additive migrations** that are gated on approval (none is required
for a correct, RLS-safe read + write slice on the existing schema):
1. **Unique partial index** on `reservations(restaurant_id, table_id, reservation_date)` `WHERE status IN
   ('pending','confirmed')` — the only real defense against concurrent double-booking. Additive, non-breaking.
2. **Reservation-code generation RPC** (the deferred "0007" pattern) to atomically allocate collision-free
   `reservations.code` / table uniqueness — replaces the length-based client generator. Additive.
3. (Optional) **Table-status auto-sync RPC** (Option 2 in F) to update `restaurant_tables.status` from
   reservation events under a permissions-safe definer — additive.
Migrations 0001–0006 are **unchanged**. No migration is applied in this audit phase. If any of the above is
approved, it ships as a separate additive migration with its own RLS policy verification (definer-scoped, no
policy changes to existing tables, no service_role).

## L. Decisions requiring user approval

These block implementation and must be confirmed before Phase 4D code is written:

1. **Reservation "delete" semantics** — use **status → `cancelled`** (non-destructive, recommended) with
   hard DELETE kept out of the default UI? Or expose a hard DELETE (Owner-only)? — RECOMMEND cancel-only.
2. **Concurrency fix (migration)** — approve adding the **partial unique index** (#J1) so double-bookings are
   DB-enforced, or keep conflict as an app-level best-effort check only? — RECOMMEND the partial unique index
   (small, additive, non-breaking).
3. **Reservation-code generation** — approve the **0007 codegen RPC** (atomic server codes) versus keeping a
   client/simple generator (higher collision risk)? — RECOMMEND the RPC once 4D writes create rows.
4. **Table-status auto-sync** — accept **Option 1** (manual Owner-only table status, floor plan read-only to
   managers/waiters) or approve the **additive auto-sync RPC** (Option 2) so reservation events update table
   status automatically? — RECOMMEND Option 1 for 4D scope.
5. **Link existing customers on reservation** — when creating a reservation, should the form **look up / link
   an existing `customers` row** by name/phone (using `customer_id`), or keep the **free-text `guest_name`
   snapshot** (walk-in model) only? — RECOMMEND keep free-text snapshot for 4D (existing UI behavior), with
   customer linkage as an optional enhancement.
6. **Past-reservation auto-rollover** — auto-mark past `pending/confirmed` reservations as `completed`? —
   RECOMMEND **no** auto-rollover in 4D (surface as-is; conflicts only checked on non-past dates).
7. **Status transition strictness** — enforce a guided lifecycle (pending→confirmed→completed, any→cancelled)
   or keep free-form status edits (current behavior)? — RECOMMEND guided transitions in the UI but still
   allow the DB's full enum.
